แจ้งรายการก่อนลงมือและได้รับอนุมัติแล้ว — ไฟล์เดียวในตาราง M1–M13 ที่เฟสนี้แตะคือ

| # | ไฟล์ | สิ่งที่เปลี่ยน |
|---|---|---|
| **M9** | `app/api/line/webhook/route.ts` | เพิ่มคำสั่ง "ผูกบัญชี" และ "แจ้งปัญหา" ในแชท 1:1 ก่อนตกไปให้ RAG ตอบเหมือนเดิม |

**ไฟล์ M อื่นไม่แตะเลย**

- ไม่แตะ `schema.prisma` (M1/M2) — model `Notification` `NotificationDelivery` และ field `lineUserId` มีครบตั้งแต่ Phase 0
- ไม่แตะ `package.json` (M11) — `nodemailer` ติดตั้งอยู่แล้ว
- ไม่แตะ `.env` (M13) — ใช้ `SMTP_*` / `GMAIL_*` / `LINE_*` และ `NEXT_PUBLIC_BETTER_AUTH_URL` ที่มีอยู่
- ไม่แตะ `lib/auth.ts` (M4) — สร้าง `lib/mailer.ts` แยก transporter ของตัวเองแทน
- ไม่แตะ `sidebar-data.ts` (M5) — กระดิ่งอยู่บน Header · การตั้งค่าอยู่ในหน้าที่มีเมนูแล้ว

ไฟล์เดิม **นอกตาราง M** ที่จำเป็นต้องแตะ (แจ้งไว้ก่อนลงมือเช่นกัน)

- `app/(main)/_components/header/header.tsx` — ติดกระดิ่ง 2 บรรทัด

## 4. การตัดสินใจเชิงออกแบบ

| # | เรื่อง | เหตุผล |
|---|---|---|
| 1 | **การแจ้งเตือนล้มเหลวต้องไม่ทำให้งานหลักล้มเหลว** | ทุกฟังก์ชันใน service กลืน error เอง · route เรียกแบบ `void` ไม่ `await` — ผู้แจ้งไม่ควรรอหน้าจอค้างจนกว่าเมลจะออก |
| 2 | **บันทึกผลส่งทุกช่องทางลง `NotificationDelivery`** | ตอบได้ว่าที่ผู้ใช้บอก "ไม่ได้รับ" นั้นระบบส่งไม่ผ่านจริง หรือส่งแล้วแต่ตกหล่นปลายทาง |
| 3 | **แยก "ใครควรได้รับแจ้ง" ออกจาก "ส่งอย่างไร"** | `ticket-notify.ts` เก็บกฎธุรกิจ · `notification.ts` เก็บกลไกช่องทาง — แก้ถ้อยคำหรือเพิ่มช่องทางได้โดยไม่ปนกัน |
| 4 | **บันทึกภายในไม่ส่งแจ้งเตือนถึงผู้แจ้ง** | ผู้แจ้งไม่เห็นข้อความนี้ในหน้าจออยู่แล้ว ถ้าส่งไปด้วยเนื้อความภายในจะรั่วออกทางอีเมล/LINE |
| 5 | **ไม่แจ้งเตือนคนที่เป็นผู้ทำรายการเอง** (`skipIfActor`) | ไม่มีใครอยากได้เมลบอกสิ่งที่ตัวเองเพิ่งกดไปเมื่อสองวินาทีก่อน |
| 6 | **ตั้งค่ารายบุคคลเก็บใน `AppSetting` คีย์ `notification.prefs.<userId>`** | เป็นค่าตั้งค่าล้วนที่อ่านทีละคน · เลี่ยง migration กับฐานข้อมูลจริงตาม §16.5 ข้อ 3 · ถ้าวันหนึ่งต้องคิวรีข้ามผู้ใช้จำนวนมาก ค่อยย้ายเป็นตารางของตัวเอง |
| 7 | **สร้างแถว `Notification` เสมอ แม้ผู้ใช้ปิด in-app** | `NotificationDelivery` ต้องมีแถวแม่ให้อ้างถึง และเป็นบันทึกว่าเคยแจ้งอะไรไปบ้าง · กรณีปิด in-app จะทำเครื่องหมายว่าอ่านแล้วตั้งแต่ต้น กระดิ่งจึงไม่ขึ้น |
| 8 | **ผูกบัญชี LINE ด้วยรหัส 6 หลัก ไม่ใช่พิมพ์อีเมล** | ถ้าให้พิมพ์อีเมลใน LINE ใครก็สวมสิทธิ์คนอื่นได้ · รหัสออกจากหน้าโปรไฟล์ที่ล็อกอินอยู่แล้วเท่านั้น |
| 9 | **บัญชี LINE หนึ่งผูกได้กับผู้ใช้เดียว** | `lineUserId` เป็น unique · ถ้าซ้ำจะตอบให้ไปยกเลิกจากบัญชีเดิมก่อน แทนการแย่งสิทธิ์เงียบๆ |
| 10 | **F1.9 รับแจ้งเฉพาะแชท 1:1 ที่ผูกบัญชีแล้ว** | ในกลุ่มระบุตัวผู้แจ้งไม่ได้ · ยังไม่ผูก = ไม่รู้ว่าใครแจ้ง จะสร้างใบให้ใครไม่ได้ (บอทตอบวิธีผูกให้) |
| 11 | **Ticket ที่แจ้งทาง LINE ตั้ง Impact/Urgency เป็นกลางทั้งคู่** | แชทไม่ได้ถามระดับความรุนแรง · ตั้งกลาง = priority ปานกลาง แล้วเจ้าหน้าที่ปรับได้ภายหลัง (F2.4) |
| 12 | **กระดิ่งใช้ polling 60 วินาที ไม่ใช่ WebSocket** | ระบบยังไม่มีชั้น realtime และงาน Helpdesk ไม่ต้องการความเร็วระดับวินาที · หยุด poll เมื่อผู้ใช้สลับไปแท็บอื่น |

## 6. ค้างไว้ / ต้องทำต่อ

1. 🔴 **ลิงก์ในอีเมลและ LINE ยังชี้ `localhost`** — ประกอบจาก `NEXT_PUBLIC_BETTER_AUTH_URL`
   ซึ่งตั้งเป็น `http://localhost:3000` ใน `.env` และ `http://localhost:8810` ใน `.env.production`
   **ก่อนใช้งานจริงต้องแก้เป็นโดเมนจริง** ไม่งั้นผู้รับกดลิงก์ในเมลแล้วเปิดไม่ได้
   (เป็นตัวแปรในตาราง M13 จึงต้องขออนุมัติก่อนแก้)

2. **ยังไม่ได้ทดสอบ LINE รายบุคคลกับบัญชีจริง** — ทดสอบด้วย `lineUserId` ปลอม ซึ่งพิสูจน์ได้แค่ว่า
   ระบบเรียก LINE API จริงและบันทึกผลล้มเหลวถูกต้อง · การส่งถึงคนจริงต้องให้เจ้าของบัญชี
   พิมพ์ "ผูกบัญชี &lt;รหัส&gt;" ในแชทกับบอทก่อน

3. **หมวดหมู่ของ Ticket ที่แจ้งทาง LINE** — ยังไม่มีการถามหมวดหมู่ในแชท
   ระบบส่งเข้าหมวดที่ตั้งใน `AppSetting` คีย์ `ticket.line_default_category` (เก็บเป็น slug)
   ถ้าไม่ได้ตั้งจะใช้หมวดที่ `sortOrder` ต้นสุด · **ยังไม่มีหน้าจอให้ตั้งค่าคีย์นี้**

4. **`approval_requested` / `approval_decided` / `task_assigned` ยังไม่มีใครเรียก** —
   เตรียมชนิดและเทมเพลตไว้ใน service แล้ว รอ API ของเฟส 5 (SDLC) และเฟส 7 (คำขออนุมัติ)

5. **กระดิ่งใช้ polling 60 วินาที** — การแจ้งเตือนจะขึ้นช้าสุด 1 นาที
   ถ้าต้องการทันที ต้องเพิ่มชั้น realtime (SSE / WebSocket) ซึ่งอยู่นอกขอบเขตเฟสนี้

6. **ยังไม่มีหน้ารวมการแจ้งเตือนทั้งหมด** — dropdown แสดง 10 รายการล่าสุด
   รายการเก่ากว่านั้นยังไม่มีหน้าให้เปิดดู (API รองรับ pagination ไว้แล้ว)

7. **ยังไม่มีการล้างการแจ้งเตือนเก่า** — ตาราง `Notification` และ `NotificationDelivery`
   จะโตขึ้นเรื่อยๆ ควรมีงานลบรายการที่เก่ากว่า 90 วันในเฟสถัดๆ ไป

8. **ของค้างจากเฟสก่อนที่ยังไม่ได้แตะ**
   - F1.7 ไฟล์แนบ Ticket — ยังต้องตัดสินใจว่าจะเก็บไฟล์ที่ไหน
   - F3.9 Widget บน Dashboard — เลื่อนไป Phase 8 (M8)
   - ยังไม่มีเจ้าหน้าที่จริงในระบบ → `ServiceCategory.defaultAssigneeId` ยังว่างทุกหมวด
     ทำให้ Ticket ที่แจ้งเข้ามายังไม่มีใครถูกมอบหมายอัตโนมัติ และไม่มีใครได้รับแจ้งเตือนรายบุคคล
   - ยังไม่ได้ทดสอบด้วย role `student` / `user` / `agent`
   - `pnpm lint` ทั้งโปรเจกต์ยังมี error เดิมในไฟล์กลุ่ม "ไม่แตะเลย"
   - โลโก้/ชื่อแอปใน sidebar ยังเป็น "AI Native"
